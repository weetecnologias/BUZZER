# AGENTS.md — working on BUZZER

Instructions for AI coding assistants (and humans) changing this repository. Read this first, then
[docs/developer-guide.md](docs/developer-guide.md) for detail. The Next.js admin has its own
[apps/admin-web/AGENTS.md](apps/admin-web/AGENTS.md) (generated by `next dev`): read it before touching that app.

## Keep this file current

- Read this file **before every change**, and follow it so existing behaviour keeps working.
- In the **same change**, update this file whenever you add or change a command, a convention, a module, a shared helper, a setting
  pattern or a rule that the next person must know. If nothing here is affected, leave it alone.
- `CLAUDE.md` only imports this file (`@AGENTS.md`) so Claude Code loads it automatically; keep the content here.

## Git rules (non-negotiable)

- **Never push to `main`.** Only the user opens and merges the final `feature/buzzer-platform-mvp` → `main` pull request.
- Push only to the `wee` remote (`weetecnologias/BUZZER`). The `origin` remote is never pushed to.
- Commit and push **only when the user asks**.
- **One branch per change.** `feature/buzzer-platform-mvp` is the integration branch; never commit to it directly. Each change gets
  its own branch cut from it, then a pull request **into `feature/buzzer-platform-mvp`** (never into `main`):
  - stages: `feature/stage-<n>-<short-name>` (e.g. `feature/stage-8-tasks-errands`)
  - bug fixes: `fix/<short-name>`; docs only: `docs/<short-name>`; tooling: `chore/<short-name>`
  - If the previous change's PR is not merged yet and the new work needs it, cut the new branch from that branch; once the earlier PR is
    merged its PR shows only its own changes.
  - Start: `git fetch wee && git switch -c <branch> wee/feature/buzzer-platform-mvp`; push: `git push -u wee <branch>`; PR:
    `gh pr create --repo weetecnologias/BUZZER --base feature/buzzer-platform-mvp --head <branch>`.
- The transformation is built in stages (see [docs/transformation-plan.md](docs/transformation-plan.md)); each stage needs the user's
  go-ahead before the next one starts.

## Run and check

No Docker or PostgreSQL install is needed: local dev and tests use embedded PostgreSQL (zonky).

| Task | Command |
|---|---|
| Backend (port 8080, data in `backend/.local-data/`) | `cd backend && mvn spring-boot:test-run -Dspring-boot.run.main-class=com.buzzer.LocalDevApplication` |
| Backend tests (all must pass) | `cd backend && mvn test` (one class: `mvn test -Dtest=MarketplaceFlowTest`) |
| Admin (port 3000) | `cd apps/admin-web && npm run dev`; check with `npx tsc --noEmit` and `npx next build` |
| Mobile apps (web) | `cd mobile && npm --workspace @buzzer/customer-app run web -- --port 8081` (partner 8082, agent 8083) |
| Mobile typecheck | `cd mobile/apps/<app> && npx tsc --noEmit -p .` (or `cd mobile && npm run typecheck`) |

`.claude/launch.json` defines the same five servers. Dev sign-in is OTP: in the dev profile the OTP is returned by the API and shown on
screen; test logins are in `docs/developer-logins.xlsx`. Payments run on a test-mode gateway (the apps show "Simulate success / failure").

Before saying a change is done: backend compiles and the **full** test suite passes, every touched app typechecks, the admin build passes,
and user-facing changes are checked in the running app.

## Backend conventions

- **Data access:** `JdbcClient` + Java records, plain SQL. No JPA / ORM.
- **API shape:** everything under `/api/v1`. Success = `ApiResponse` `{ "data": … }`; errors = `{ "error": { code, message, details } }`
  from `BusinessException` + `ErrorCode` (add new codes there, with the HTTP status). JSON is **snake_case** (Jackson); query params are
  camelCase (`?categoryId=`).
- **Access control:** URL rules in `identity/SecurityConfig` plus `@PreAuthorize` on controllers. Every endpoint is scoped to the caller's
  own data — return `notFound` (not 403) for other people's records. Customer endpoints need the CUSTOMER role, so agents can never
  accept, pay or approve for a customer. Work an agent prepares for a customer goes through `agent/DraftService` (customer approves in
  their app); log agent actions with `AgentActivityService.log(...)`.
- **Creating things:** endpoints that create requests, orders, bookings or payments take an `Idempotency-Key` header; a retry returns the
  same record.
- **Request hub:** every customer request is a `service_requests` row (`request_type`, `vertical`, `lifecycle`). Lifecycle `REQUEST_V1`
  uses `RequestStatus` and `RequestRepository.transition(...)`; lifecycle `ORDER` statuses are driven by the order module and mirrored with
  `RequestRepository.mirror(...)`. `Row.statusEnum()` throws for order rows — check `row.isV1()` in code that can see both. Write every
  meaningful step to the timeline (`request_status_history`, via `transition` / `note`).
- **Money:** only a verified payment-gateway webhook marks a payment paid; refunds are created PENDING for finance to approve. Order lines
  and order money are immutable (database triggers).
- **Marketplace visibility:** use the shared fragments in `marketplace/MarketplaceSql` (`VISIBLE_SHOP`, `VISIBLE_LISTING`,
  `NEAREST_LOCATION`) rather than re-writing the rules.
- **Settings, not constants:** business numbers (timeouts, counts, radii, fees) live in `platform_settings` via `SettingsService`.
  First-response SLA per vertical comes from `ops/SlaPolicy` (`vertical_sla` table), not a constant.
- **Java text blocks:** trailing spaces at line ends are stripped, so join SQL fragments with an explicit `" "`
  (`""" … AND""" + " " + FRAGMENT`); never put `" + VAR + "` inside a text block.

## Database migrations

- **Additive only**: new tables / columns / constraints; never drop or rewrite data in place. Backfill existing rows in the same migration.
- Next production migration number = highest `V*` in `db/migration` + 1 (check the folder — uncommitted work may already use the next
  number). Dev seeds follow the same rule in `db/devseed`.
- On a fresh database the dev seeds (`V1000+`) run **after** all migrations, so a migration's backfill does not see seeded rows: repeat the
  backfill in an idempotent dev seed (`ON CONFLICT DO NOTHING`) when it matters. On an existing dev database Flyway runs new migrations
  out of order (dev profile), after the seeds.
- New seeded logins → add them to `docs/developer-logins.xlsx`.

## Backend tests

- Integration tests extend `support/IntegrationTest` (full Spring context, embedded PostgreSQL with migrations + dev seed) and call the API
  through `support/ApiClient` (`login`, `get`, `post`, `put`, `call`, `ApiClient.key()` for idempotency keys).
- All test classes share **one** database: use random phone numbers for new users, and restore any global state you change (settings,
  partner hours, vertical switches) in a `finally` block.
- Each transformation stage adds an acceptance test class named after the journey (e.g. `MarketplaceFlowTest`, `ServiceBookingFlowTest`).
- If a run fails with an embedded-PostgreSQL `initdb` error, it is environmental — run it again.

## Frontend conventions

- Mobile apps share `@buzzer/core`: theme tokens, `api` client (`get/post/put/del/upload/download`, `ApiError` with `code`), `useQuery` /
  `useAction`, the custom `StackNavigator` (`useNav().push/replace/pop`), UI kit (`Screen`, `Card`, `Button`, `Chip`, `Notice`,
  `ConfirmDialog`, `StatusBadge`, `Timeline`, `AttachmentList`). Add shared status labels in `format.ts` and icons in `glyphs.ts`.
- Unmount a `ConfirmDialog` that can be closed right before navigating (`{open ? <ConfirmDialog visible … /> : null}`); on web a modal
  that is still fading out can stay stuck on screen.
- Admin pages use `useApi` / `useMutation` from `@/lib/api` and components from `@/components/ui`. A new backend area for the admin must be
  added to the `ALLOWED` list in the BFF route.
- Keep copy plain and customer-friendly; never promise what the backend does not do (e.g. real-time stock, a live payment gateway).
